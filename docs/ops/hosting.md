## 1. Architectural Distribution Boundaries (FD-160)

Per decision **FD-160** ([docs/plan/frontend/decisions.md](../plan/frontend/decisions.md)), the hosting architecture maintains a strict distinction between what operates locally inside the habitat and what is hosted publicly for judges and external review:

### What Stays on the Habitat LAN (Runtime System)

- **Hab Core Server:** Runs locally on Node.js with Fastify and `ws` at `0.0.0.0:8080` ([docs/specs/02_Technical_Requirements_Document.md](../specs/02_Technical_Requirements_Document.md) §A.5, §B).
- **Mission Clock & State Engine:** The authoritative mission clock (operating at 1×, 10×, or 60× sim speed), real-time simulation engine, WebSocket telemetry fan-out (≤ 10 Hz), and safety logic modules run strictly on the habitat server ([docs/specs/02_Technical_Requirements_Document.md](../specs/02_Technical_Requirements_Document.md) §D.14).
- **Local Asset Serving:** The server serves the web application build (`apps/web/dist`), tile pyramids (`data/sites/<site_id>/tiles/`), binary grids (`data/sites/<site_id>/grid/`), vectors (`vectors/`), and POI images (`images/`) directly over the habitat LAN ([docs/specs/02_Technical_Requirements_Document.md](../specs/02_Technical_Requirements_Document.md) §E.1).
- **Offline Integrity (NFR-01, NFR-08):** No internet connection is used or required at runtime. Astronaut suit tablets (SCR-12), HUDs (SCR-13), and ops consoles (SCR-11) connect exclusively to the Hab Core via the local travel router or Wi-Fi switch ([docs/ops/demo-kit.md](demo-kit.md)).

### Submission Access

- **Public Replay Link (Vercel, 2026-11-14):** A static deployment of the web application (`apps/web`, package 27; [docs/specs/01_Product_Requirements_Document.md](../specs/01_Product_Requirements_Document.md) FR-34) with the site bundle under `sites/`, at <https://gale-surface-ops.vercel.app> (replay: `#/replay`), built by Vercel from `main` (§5). The Hab Core is not hosted there, so the live roles (ops, EVA, HUD, join) need the habitat LAN. FD-160 and [02 §B](../specs/02_Technical_Requirements_Document.md#b-technology-choices) still name GitHub Pages; the spec sync is open for the team.
- **Static Recording Data:** The public replay page reads a static recording (`scenarios/storm-sol4190/recording.json`) generated by `make record` (T27.05, T22.14, BD-105). It reproduces the sol 4190 storm timeline, crew telemetry, and alerts directly in the client browser without requiring a running Hab Core server or local network connection.
- **Large Site Bundle:** The complete site bundle (tiles, 5 m routing grid and POI images) is tracked through Git LFS for deployment from main (§5); the release archive remains available to the team.

## 3. Team Release Asset Fetch Route

Team members and clean-clone environments download and verify the site bundle using the following documented procedure ([docs/ops/feasibility.md](feasibility.md)):

1. Sign in to GitHub CLI with an account having repository access. Download the site bundle release asset:

   ```sh
   gh release download data-gale_boxwork-2026.11.09 -p 'gale_boxwork-2026.11.09.zip' --repo tashobi02/CheesySpace-NasaSpaceAppChallenge
   ```

   Verify the downloaded zip SHA-256 against [the lane plan](../plan/README.md#6-environment-notes) before extracting it.

2. Unpack the downloaded bundle in a temporary directory for verification. Compare each file with `data/sites/<site_id>/site-manifest.json` ([docs/specs/05_Backend_and_Database_Schema.md](../specs/05_Backend_and_Database_Schema.md) §Site). For each asset, verify that the SHA-256 digest matches `sha256`.
3. If hashes match, extract the bundle contents into `data/sites/<site_id>/`, preserving the `tiles/`, `grid/`, `vectors/` and `images/` directory structure ([docs/specs/02_Technical_Requirements_Document.md](../specs/02_Technical_Requirements_Document.md) §E.1). Stop immediately if an asset is missing or a hash differs.

Obtain the bundle before running the full application. NFR-01 requires no internet at runtime; NFR-08 requires LAN-only operation without third-party requests ([docs/specs/02_Technical_Requirements_Document.md](../specs/02_Technical_Requirements_Document.md) §F). Downloaded datasets are kept out of Git ([CLAUDE.md](../../CLAUDE.md) §2). Since 2026-11-14 the `gale_boxwork` tiles, grid and images are also tracked with Git LFS (§5), so a clone with `git lfs install` already has them; this release-asset route stays for archive copies.

## 5. Public Link Deployment (Vercel)

- **Project:** Vercel project `gale-surface-ops` (team `tashobi`), connected to this GitHub repository; production alias <https://gale-surface-ops.vercel.app>. Pushes to `main` deploy to production; other branches get preview deployments.
- **Site bundle in Git LFS (2026-11-14, Obidit Islam):** `data/sites/gale_boxwork/{tiles,grid,images}/` are tracked with Git LFS ([.gitattributes](../../.gitattributes)), so the Vercel build has them. This supersedes the release-asset-only route chosen in [feasibility](feasibility.md#large-tiles-in-the-repo) for the Git copy; `pipeline/work/` stays git-ignored. **Git LFS must be enabled** in the Vercel project (*Settings → Git → Git LFS*), otherwise the build receives pointer files.
- **Build:** [vercel.json](../../vercel.json) runs `npm ci`, `npm run build` and [scripts/vercel_build.mjs](../../scripts/vercel_build.mjs), which copies `data/sites/` to `apps/web/dist/sites/` and fails the build when a hashed manifest asset is missing or differs (§3 step 2), so a pointer file or stale bundle never reaches the link.
- **New bundle:** commit the new tiles, grid and images together with the new `site-manifest.json`.
